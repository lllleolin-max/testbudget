# Architecture and supported boundaries

`core.py` normalizes identities/numbers, partitions prior evidence by (ID, environment, revision), computes support-aware descriptive indices and enumerates all bounded subsets. Online Pareto filtering retains feasible candidates. `workflow.py` verifies a deterministic frozen plan, validates observed execution rows and atomically serializes history. `cli.py` binds file inputs to these APIs; `examples` implements disclosed data and retrospective comparisons; the separate test oracle independently enumerates feasible subsets and Pareto dominance.

For H attempts and N units: normalization O(H log H + N log N), evidence O(H log H) worst case. Search visits at most min(2^N, max_states) subsets. Version 0.2 prepares exact common-denominator coefficients, group signal tiers and requirement bitmasks once, then updates changed units in the original ascending binary-mask order. Carries toggle fewer than two units per mask on average; changed group maxima can still inspect O(N) tiers. The solver checks R bitmask requirements and compares against frontier F in O(F). Worst-case search remains O(S*(N+R+F)) for S visited subsets; exact integer operation cost depends on bit length. F can be exponential. Storage includes O(H+N+declared tags/requirements+N*F), because each retained point contains selected IDs. There is no all-subset cache. Reverification repeats the bounded search. This is deliberately not a scalable suite-level service. At most 20 units enter exact search; up to 2000 catalogue units are accepted and then produce UNKNOWN without pretending search completed. Default max_states completely searches <=18 units; raise it to >=2^N for <=20 units. Larger suites should declare genuinely runnable execution groups upstream; grouping semantics and costs are caller responsibility. See [search work](SEARCH.md) for reproduction and measured adverse cases.

`FEASIBLE` guarantees the selected tuple satisfies declared constraints and rational reserved budget. `complete: true` also establishes exhaustive Pareto/utility optimum within this model. An incomplete FEASIBLE answer is a checked upper bound on minimum feasible cost and lower bound on achievable modeled utility, with no optimality proof. `INFEASIBLE` means every subset was checked. `UNKNOWN` means no feasible candidate found under the bound; it is not proof of impossibility. Empty catalogue/zero budget can be feasible when no requirements exist.

Supported history assumes one ordered revision stream and environment label per requested unit. This tool does not interpret Git DAG ancestry, changed-code coverage, parameter interactions, probabilistic correlation, parallel workers, shared setup amortization, quarantine automation, calibrated detection confidence, or actual failure diagnosis. Distinct parameterizations need distinct IDs. Adapter grouping or branching errors cannot be inferred from a JSON trace. Mandatory groups and coverage are explicitly configured; absence of a requirement is not a promise of coverage.

Workflow outputs use temp-file fsync + atomic replacement in the destination directory. They are single-writer snapshots: there is no process lock or merge service; coordinate CI writers externally. A history edit before the target invalidates record ingestion. Identical result replay is idempotent; conflicting attempts fail. Do not overwrite another job's history with an old snapshot. The plan digest detects accidental edits and recomputation catches altered selections; it authenticates no origin. The SDK trusts caller-provided evidence and labels. Keep a controlled history store.

Run actual tests through your CI runner after selection. Emit an execution object with matching plan digest and observed durations; every selected unit needs an observation, runs are bounded by its reservation, target and environment must match. Partial runs must be reconciled by the adapter before complete ingestion. Actual durations are preserved; an estimated reserve is not a hard timeout. Retain plans and runner logs for audits.
